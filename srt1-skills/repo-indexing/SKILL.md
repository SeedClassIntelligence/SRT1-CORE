# Repo Indexing Skill

> **Skill ID:** `SRT1-SKILL-001`
> **Module:** SRT-1 Engine
> **Authority:** Repo Understanding
> **Classification:** Public Core
> **Mutates Source:** Never

## Purpose

Repo Indexing reads a registered repository or module and builds the factual
repository map used by SRT-1: file inventory, hashes, symbols, dependencies,
language coverage, duplicate findings, and manifest metadata.

It is the foundational Repo Understanding skill. Downstream skills may consume
the manifest, symbol table, and dependency map, but they do not redefine
repository truth.

## Activation

| Trigger | Source | Frequency |
|---|---|---|
| Engine startup | `SRT1Engine.__init__()` -> index pipeline | Once per runtime start |
| Repository activation | Repository Manager / registered repo load | On demand |
| File change detected | File watcher / manifest freshness check | On change |
| Manual re-index | `POST /api/reindex` | On demand |
| MCP/context request | Context request when manifest is stale | On demand |

## Preconditions

- `workspace_root` exists and is readable.
- Requested scan root resolves inside the registered repository boundary.
- Ignore rules and excluded directory rules are available.
- No active boundary lockout prevents indexing.

## Inputs

| Input | Type | Source |
|---|---|---|
| `workspace_root` | Absolute path | CLI, Engine constructor, or Repository Manager |
| Source files | File system | Directory walk with extension filter |
| `.gitignore` patterns | Text | Repository ignore rules |
| Supported extensions | Set | Parser/indexer configuration |
| Prior manifest metadata | JSON/dict | Freshness and hash comparison |

## Outputs

| Output | Type | Destination |
|---|---|---|
| `symbol_table` | Dict | Engine memory / manifest |
| `call_graph` / dependency map | Dict | Engine memory / manifest |
| `curation_report` | Dict | Engine memory / dashboard |
| `srt1_code_manifest.json` | JSON | Repository root or configured manifest path |
| `file_tree` | Dict | Dashboard / API |
| `language_coverage` | Dict | Manifest / dashboard |
| `manifest_hash` | String | Integrity metadata |

Context documents may be regenerated by Reinjection/context generation after
indexing, but the repo-indexing skill itself owns repository facts, not final
assistant prompt composition.

## Runtime Responsibilities

1. Walk the directory tree while respecting ignore and exclusion rules.
2. Dispatch files to the appropriate parser.
3. Extract symbols, imports, functions, classes, and dependency evidence.
4. Compute file hashes for freshness and integrity checks.
5. Detect duplicate files and functional overlap candidates.
6. Produce manifest and dashboard-ready repository structure.
7. Label degraded/partial results when parser coverage is incomplete.

## Boundary Rules

| Rule | Enforcement |
|---|---|
| Only read files inside `workspace_root` | Path canonicalization and boundary check |
| Never mutate source files | Writes only generated manifest/index outputs |
| Respect ignore rules | `.gitignore` and internal exclusions |
| Skip generated/runtime folders | `.git`, `.srt1`, `node_modules`, caches, virtualenvs, build output |
| Skip unsafe or oversized files | Extension filter and size guard |

Execution actors do not call this skill directly. After an execution actor
changes files, SRT-1 observes the change and re-indexes through its own
repository understanding path.

## Verification

| Check | Success condition |
|---|---|
| Symbol table populated | Parseable source files produce symbol entries or a clear degraded reason |
| Manifest written | Manifest exists and is valid JSON |
| Manifest hash computed | Integrity metadata includes a manifest hash |
| No critical boundary violations | Curation report has no hard-stop findings |
| Runtime remains bounded | Indexing does not recurse into ignored/generated folders |

Failure indicators include an empty symbol table without explanation, manifest
write failure, repeated parser crashes, or indexing time that suggests recursive
inclusion of generated folders.

## Events

These events are public Core-safe observability events. They may be emitted into
SRT-1's local event/tracing system and may later be marked as signature-eligible
metadata. A developer may create or attach a Seed Signature from inside SRT-1,
but the standalone Seed Signature platform performs the signing and returns the
trust metadata.

| Event | Severity | Status |
|---|---|---|
| `repo_index_started` | info | planned |
| `repo_index_completed` | info | planned |
| `repo_index_failed` | high | planned |
| `manifest_freshness_degraded` | medium | planned |

Public Core may expose trust/freshness metadata and broker Seed Signature
attachment. It does not ship the Seed Signature platform, private keys, private
signing service, or private audit chain.
